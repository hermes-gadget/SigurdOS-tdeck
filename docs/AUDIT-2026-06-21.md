## CONFIRMED BUGS

### 🔴 HIGH — Click button has no deadtime enforcement (unlike all directional buttons)

| Field | Value |
|-------|-------|
| **File:Line** | `src/hal/trackball.cpp:191-211` |
| **Function** | `scan_click()` |
| **Severity** | HIGH |
| **Status** | CONFIRMED |

**Root cause:** `scan_click()` calls `queue_event(btn.event)` at line 207 but never sets `btn.last_event_at`. Every directional button (`scan_direction()` at line 188) sets `btn.last_event_at = now;` to enforce deadtime (80ms for LEFT, 150ms for others). The click button (shared GPIO 0 with BOOT button) has zero deadtime — a bouncing press can queue multiple click events.

**Reproduction:** Rapidly press the trackball center button. Observe multiple click events fire (if bounce exceeds the 20ms debounce window).

**Fix:**
```cpp
// After line 207 (queue_event(btn.event)):
btn.last_event_at = now;
```

### 🔴 HIGH — Trace screen timer overwrite: use-after-free on rapid taps

| Field | Value |
|-------|-------|
| **File:Line** | `src/ui/screens/screen_trace.cpp:146` |
| **Function** | Trace screen contact click handler |
| **Severity** | HIGH |
| **Status** | CONFIRMED |

**Root cause:** Each contact tap creates a new `lv_timer` via `g_trace_poll_timer = lv_timer_create(...)` WITHOUT deleting the previous timer. If two contacts are tapped within 500ms, two timers run concurrently. When the first timer fires, it reads `trace_result_label` which may have been freed by `lv_obj_del_async()` in the second tap's handler. Both timers also call `lv_timer_del(t)` on themselves, so only the owner is deleted — the sibling timer leaks and runs with a stale label pointer.

**Fix:**
```cpp
// Before line 146:
if (g_trace_poll_timer) {
    lv_timer_del(g_trace_poll_timer);
    g_trace_poll_timer = nullptr;
}
```

| Field | Value |
|-------|-------|
| **File:Line** | `src/mesh/mesh_wrapper.cpp:191` |

### 🟡 MEDIUM — BLE validation writes to SPIFFS every 5 seconds (flash wear)

| Field | Value |
|-------|-------|
| **File:Line** | `src/mesh/mesh_wrapper.cpp:112-119` |
| **Function** | `bleValidationEmit()` |
| **Severity** | MEDIUM |
| **Status** | CONFIRMED |

**Root cause:** The BLE validation log opens, appends, and closes `/ble_hw.txt` every 5 seconds. SPIFFS has limited write endurance (~100K erase cycles per block). Running BLE validation mode for extended periods will accelerate flash wear.

**Fix:** Guard with `#ifndef NDEBUG` so production builds never hit this path, or reduce write frequency (e.g., buffer in RAM and flush every 60s).

### 🟡 MEDIUM — `SPIFFS.end()` in radio setup "Apply" handler: aggressive pre-reboot pattern

| File:Line | `src/ui/screens/screen_radio_setup.cpp:550` |
|-----------|---------------------------------------------|
| **Severity** | MEDIUM (latent risk, no known crashes) |
| **Status** | CONFIRMED |

**Root cause:** The radio setup "Apply" button handler calls `SPIFFS.end()` at line 550, then `delay(200)`, then `ESP.restart()`. The `SPIFFS.end()` is correct pre-reboot housekeeping, but any code path between `end()` and `restart()` that touches SPIFFS would fail. Currently safe because the delay is short and there are no intervening SPIFFS operations, but fragile if future code is added.

**Also affects:** `src/ui/onboarding_screen.cpp:414` (same pattern).

**Fix:** Move `SPIFFS.end()` to the last possible line before `ESP.restart()`, or accept the pattern with a comment documenting the invariant.

## RISKS & FRAGILE PATTERNS (not crashing today, but fragile)

### 🟡 MEDIUM — GPS: `Serial1.readBytesUntil()` with unbounded wait on NMEA sentences

| File:Line | `src/hal/gps.cpp:211` |
|-----------|----------------------|
| **Severity** | MEDIUM |
| **Status** | CONFIRMED (design concern) |

**Root cause:** `Serial1.readBytesUntil('\n', buf, sizeof(buf)-1)` blocks until a newline or buffer fill. If GPS is connected but producing garbage (no newlines), this call blocks indefinitely, stalling the GPS poll task. The poll interval is 1 second, so impact is a 1-second stall per cycle — manageable but could be hardened.

**Fix:** Use `Serial1.setTimeout(100)` before the read, or use `Serial1.available()` + character-by-character read with a timeout.

---

### 🟡 MEDIUM — I2C speed compromise at 200kHz (both touch and keyboard support 400kHz)

| File:Line | `src/hal/touch.cpp:112`, `src/hal/keyboard.cpp:361` |
|-----------|---------------------------------------------------|
| **Severity** | MEDIUM |
| **Status** | CONFIRMED (intentional but suboptimal) |

Both `sigurdos_touch_init()` and `sigurdos_keyboard_init()` call `Wire.setClock(200000)`. The comment says "Compromise speed for shared I2C bus." Both the GT911 touch controller and ESP32-C3 keyboard MCU support 400kHz. The clock is also set redundantly in two places.

**Fix:** Try 400kHz first, fall back to 200kHz only if I2C errors occur. Move `setClock()` to a shared init point.

---

### 🟡 MEDIUM — Clock setting redundancy: 3 different `Wire.setClock()` call sites

| File:Line | `src/hal/tdeck_board.h:71`, `src/hal/touch.cpp:112`, `src/hal/keyboard.cpp:361` |
|-----------|---------------------------------------------------------------------------------|
| **Severity** | MEDIUM |
| **Status** | CONFIRMED |

Three different files set the I2C clock. If init order changes, the final clock frequency depends on which init runs last. If touch init fails and keyboard init isn't called (possible under Launcher), the I2C bus stays at 100kHz for all remaining touch reads.

**Fix:** Move `Wire.setClock()` to a single shared init function, called once after all I2C peripherals are probed.

---

### 🟡 MEDIUM — Battery percentage lookup: latent division-by-zero

| File:Line | `src/hal/battery.h:49-53` |
|-----------|--------------------------|
| **Severity** | MEDIUM |
| **Status** | CONFIRMED (table is safe today, no guard) |

The lookup loop interpolates between adjacent table entries. If two consecutive entries in `mv_table` have the same value, `range_mv = mv_table[i] - mv_table[i+1]` would be zero, causing a division-by-zero. The current table has monotonically decreasing unique values, so this won't happen — but it's a maintenance hazard.

**Fix:** Add `if (range_mv == 0) return pct_table[i];` before the division.

### 🟢 LOW — Auto-off dialog: static `selected` pointer correct but fragile

|-----------|-----------------------------------------------------|
| **Severity** | LOW |
| **Status** | FALSE POSITIVE (subagent claimed UAF, but DELETE callback nulls correctly) |

The subagent flagged a UAF risk for the `static lv_obj_t* selected` pointer. However, the `LV_EVENT_DELETE` callback at line 360-362 nulls `selected` when the dialog is destroyed. ### 🟢 LOW — `sigurdos_shared_spi_begin()` unconditionally calls `SPIClass::begin()`

| File:Line | `src/hal/spi_shared.cpp:55-62` |
|-----------|-------------------------------|
| **Severity** | LOW |
| **Status** | NEEDS DECISION (design choice, currently safe per code comments) |

The subagent flagged this as CRITICAL (SPI2_HOST contention). The comment at spi_shared.cpp:41-42 states: "LovyanGFX (display) manages its own bus access on SPI2_HOST through the IDF SPI driver directly and is not affected by this SPI class state." The Arduino `SPIClass::begin()` and LovyanGFX's internal IDF SPI driver use separate `spi_device_handle_t` instances. On ESP32-S3, SPI2_HOST supports multiple device handles on the same bus with different CS lines. The `begin()` call issues `spi_bus_initialize()` which checks if the bus is already initialized — if LovyanGFX got there first, Arduino's begin() will get a different handle. The real concern is whether `periph_module_reset()` is called by Arduino's `begin()` — if so, it could reset LovyanGFX's handle state.

The code comment claims isolation. This needs an ESP-IDF expert to verify definitively. Meanwhile, the SD card init runs at boot before the display is actively drawing, so the practical impact is minimal.

**Recommendation:** If SD card init is moved later in boot, add explicit bus locking or move display to SPI3_HOST.

## BUILD SCRIPTS & INFRASTRUCTURE

### build_metadata.py ✅
**Clean, well-structured.** Handles git errors gracefully (returns "unknown"). Sets build-derived CPPDEFINES including `SIGURDOS_VERSION` from `git describe --tags`, falling back to the static `#define` in `tdeck_pins.h`. Uses `subprocess.run()` not `os.system()`. Well-isolated helper functions.

**Minor observation:** The `_macro_string()` escaping is heavy-handed (escapes `\` then `"`) but safe.

### merge_bin.py ✅ (with one fragility)
**Functionally correct.** Merges bootloader + partitions + firmware. Creates web flasher artifacts with SHA256 manifests. Good.

**Fragility:** Line 78 walks the framework package dir to find `boot_app0.bin`:
```python
for root, dirs, files in os.walk(os.path.join(env.subst("$PROJECT_PACKAGES_DIR"), "framework-arduinoespressif32")):
```
The directory name `framework-arduinoespressif32` is hardcoded. If the framework package changes name (e.g., version bump), `boot_app0.bin` won't be found and the web flasher will silently skip it.

**Severity:** LOW — PlatformIO framework names are stable, but worth noting.

### smoke_build_matrix.py ✅
Clean CLI tool. Supports profiles (`release`, `debug`, `roadmap`), `--dry-run`, `--fail-fast`, `--list`. The nightly CI uses `--profile roadmap` which covers 7 of 17 build envs. Well-structured dataclass-based results.

**Macros** (from `src/diagnostics/log.h`):
- `SIG_LOGE` — always active (errors)
- `SIG_LOGW` — always active (warnings)
- `SIG_LOGD` — gated on `SIGURDOS_DEBUG` (debug)

**Policy enforcement:** CI's lint job (`pr-ci.yml:134-146`) greps for raw `Serial.print*` outside the whitelist. 13 files are on the `not_migrated` allowlist — they still use raw `Serial.print*` and haven't been migrated to SIG_LOG* macros. This is tracked tech debt (referenced as "T9 migration PR" in the CI script).

**Dev vs Prod differences:**
- `-D NDEBUG` is in common flags → `assert()` is suppressed in ALL builds, including debug. Use `#ifdef SIGURDOS_DEBUG` for debug-only assertions.
- `SIG_LOGD` compiles to no-op in non-debug builds. Correct.
- `SIG_LOGE`/`SIG_LOGW` always active. Correct for embedded — you always want error/warning visibility.
- Feature debug flags (`SIGURDOS_DEBUG_MESH`, `SIGURDOS_DEBUG_UI`, etc.) are only set in per-feature debug envs. Production builds have none of these.
